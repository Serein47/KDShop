# 电商站交付手册

配合 `AGENTS.md` 使用：章程管「不做什么」，本手册管「按什么顺序做」。

## 开工三步

1. 读 `AGENTS.md`，确认本次任务涉及的待确认项（Q1–Q9）已定；未定先问，别自选。
2. **定位门禁**：看仓库里已有什么文件（`docs/`、`tests/`、迁移、CI），判断当前在 G0–G6 哪一关。以仓库为准，不以对话记忆为准。
3. 只做当前门禁内的事，过了出口标准再进下一关。

## G0 需求

**动作**：把口语需求改写成「角色 + 用户故事 + 验收线（Given/When/Then）」；列权限矩阵；列全部邮件触点。
**出口**：`docs/requirements.md` 每条需求有 ID、优先级、验收线；Q3/Q4/Q7/Q8 已定。

## G1 设计

- **数据模型**：用户、地址、商品、SKU/规格、库存、购物车、购物车项、订单、订单项、支付、发货、审计日志。
- **订单状态机**（草案，Q8 可能增减）：
  `待付款 → 已付款 → 备货中 → 已发货 → 已完成`，旁支 `已取消`、`已退款`。
  每次流转记录：触发者、时间、前后状态、原因；非法流转被数据库约束或领域层拒绝。
- **支付**：金额以服务端为准；回调验签 + 幂等键；订单状态只由支付回调推进，前端回调只用于跳转。
- **库存**：下单预占、支付扣减、超时释放；并发用条件更新或行锁，不用「先查再写」。
- **权限矩阵**：顾客 / 客服 / 运营 / 管理员，每行一个能力，每列一个角色。
- **ADR**：一决策一文件，写「背景 / 选项 / 决定 / 后果」。

**出口**：模型、状态机、API 契约、权限矩阵、部署拓扑定稿；关键决策各有 ADR。

## G2 拆分

每个 Issue 写：背景、验收线、涉及的接口与文件、依赖关系、估时。用里程碑串起一次可上线的切片。

**出口**：任意 Issue 拿给新人可以直接开工。

## G3 实现

分支 → 代码 → 测试 → 自审 → PR。PR 描述三段：改了什么 / 怎么验证 / 风险与回滚。

编码约定：
- 金额一律整数分，货币单独字段；时间存 UTC，展示按 Q7 时区
- 领域逻辑与框架解耦，能单测
- 错误统一错误码 + 用户可读文案
- 配置全部来自环境变量，启动时校验缺失项并快速失败

**出口**：CI 绿，PR 自审清单全过。

## G4 验收

命令以仓库的 `package.json` / CI 配置为准，读出来再跑，不凭记忆写命令。

- 静态：格式化、lint、类型检查
- 测试：单测（业务规则）、集成（API + 数据库）、e2e
- e2e 主线：注册 → 登录 → 搜索 → 加购 → 结算 → 支付沙箱 → 订单详情 → 后台发货 → 收到邮件
- 可访问性：键盘走通主流程，表单有标签，对比度达标

**出口**：全绿；预发环境主线 e2e 通过；缺陷清零或有书面延期。

## G5 上线

检查表：环境变量齐全、迁移已跑、种子数据就位、证书有效、邮件域名与回调 URL 配置正确、备份可恢复、回滚镜像可用、告警已接。

发布顺序：预发演练 → 生产发布 → 冒烟 → 观察窗口（看错误率与下单成功率）→ 记录到 `docs/releases/`。

冒烟用真实账号走：注册、登录、搜索、加购、下单、支付、收货邮件、后台改价。

**出口**：冒烟全过，观察窗口无异常，回滚演练做过一次。

## G6 交接

- `README.md`：项目简介、技术栈、架构图、本地启动、环境变量表、测试命令、部署步骤、常见问题
- `docs/test-accounts.md`：账号、口令、角色、能做什么；与种子脚本一致，上线后实测过
- 运维手册：日志在哪、怎么备份、怎么恢复、出问题找谁

## 事实纪律

写进任何文档的外部事实，都要能指出来源：命令输出、文件路径（带行号）、官方文档链接。
拿不准就查官方文档（`web_search` / `web_fetch`）再写；查不到就写「待确认」并给出核实动作。

## 提问方式

一次最多 3 个问题；每个问题给 2–3 个选项 + 推荐 + 代价。阻塞性问题提出后，先做不受影响的部分，不空等。

## 常见坑

- 前端传金额，后端不校验
- 支付回调不幂等，重复发货
- 库存「先查再写」导致超卖
- 下单流程同步发邮件，SMTP 一慢全站卡住
- 管理端改价、改库存没有审计
- 测试账号硬编码在代码里，上线即泄漏
