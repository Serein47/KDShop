# ADR-0002 库存扣减与 Redis 的边界

- 状态：已接受
- 日期：2026-10-27

## 背景

下单时必须决定「何时占用库存」，以及 Redis 是否参与库存事实。四种候选：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A 支付成功才扣 | 下单不占库存 | 实现最简单 | **会超卖**：付了钱才发现没货 |
| B 下单直接扣 DB | `stock -= n`，取消回补 | 一个字段，最少状态 | 无法区分「占用中」与「已售」，看板口径要额外算 |
| C 下单锁定 + 支付实扣 | `locked_stock += n` → 支付时 `stock -= n` | 语义清晰、可售量准确、不超卖 | 两个计数、三个动作、要有超时释放 |
| D Redis 预扣 + 异步落库 | Lua `DECRBY` 成功后发消息扣 DB | 高并发吞吐好 | 最终一致：要补偿、对账、重建；Redis 丢数据即超卖 |
| E DB 为准 + Redis 缓存可售量 | Redis 只做快速失败，DB 条件更新兜底 | 兼顾吞吐与正确性 | 两套状态，需要回滚缓存 |

## 决策

**采用 C。** 库存的唯一真相在 MySQL，用条件更新保证不超卖：

```sql
UPDATE sku SET locked_stock = locked_stock + #{n}
WHERE id = #{id} AND stock - locked_stock >= #{n}
```

影响行数为 0 即「库存不足」，直接失败，不做重试。

**Redis 不参与库存事实。** 它在本项目的定位是缓存与协调，不是账本：

| 用途 | 键 | 说明 |
|---|---|---|
| 登录会话 | `session:*` | Spring Session，替代 JWT |
| 验证码 / 登录限流 | `rate:login:{email}` | 5 次失败锁 15 分钟 |
| 商品详情热点 | `product:detail:{id}` | TTL 60s，改价/上下架时主动删 |
| 下单防重 | `order:submit:{userId}:{cartHash}` | SETNX + TTL 10s，挡住双击 |
| 游客购物车 | `cart:guest:{sessionId}` | 登录后合并落库 |

## 后果

- 需要 `locked_stock` 字段、超时释放任务（15 分钟扫描）、三个库存动作
- 任何时刻可对账：`stock >= 0`、`locked_stock >= 0`、二者与订单状态一致
- 单行热点更新在 MySQL 上可支撑本项目两个数量级以上的流量，不构成瓶颈

## 何时重审

满足任一条件再引入 Redis 预扣：压测下单接口 p95 > 200ms、峰值 QPS 持续 > 500、或出现秒杀类单 SKU 抢购。届时必须同时上线对账任务与缓存重建流程，否则不能上。
