# ADR-0006 会话认证与 CSRF

- 状态：已接受
- 日期：2026-10-27

## 背景

三套前端（顾客、商家、平台）同源部署，需要登录态、即时登出、按角色鉴权。候选方案：JWT 无状态令牌、服务端会话。

## 决策

用 **Spring Session + Redis 的服务端会话**，Cookie 名 `KD_SESSION`：

| 属性 | 值 | 理由 |
|---|---|---|
| HttpOnly | true | 前端 JS 读不到，XSS 拿不走 |
| SameSite | Lax | 阻断跨站 POST，保留顶层跳转带 Cookie |
| Secure | 生产 true | 只走 HTTPS |
| 空闲超时 | 30 分钟 | 与业务一致，可在 `/meta` 展示 |
| 路径 | `/` | 三套前端同源 |

**CSRF 用双提交令牌**：Spring Security `CookieCsrfTokenRepository` 写一个 JS 可读的 `XSRF-TOKEN` Cookie，前端读出来放进 `X-XSRF-TOKEN` 请求头，服务端比对。

**会话生命周期**：登录成功轮换 session id（防固定攻击）；登出删除；改密码/重置密码时删除该用户全部会话；账号被禁用时同样全量失效。

## 备选与代价

| 方案 | 放弃原因 |
|---|---|
| JWT 存 localStorage | XSS 直接拿走，且无法即时吊销 |
| JWT 存 HttpOnly Cookie | 仍然要 CSRF 防护，还要额外维护刷新令牌与黑名单，复杂度更高 |

## 后果

- Redis 成为登录链路的强依赖，Redis 挂掉 = 全员掉线（可接受，演示级）
- 服务端多实例天然支持（会话在 Redis），但定时任务仍是单实例（见架构文档）
- 未来开放第三方 API 或移动端时，需要另做一套 token 方案，不与会话混用

## 何时重审

要开放平台 API、接入移动端、或需要跨域多站点部署时。
