# ADR-0005 多商家拆单与结算

- 状态：已接受
- 日期：2026-10-27

## 背景

平台采用多商家入驻模式：顾客一次下单可能横跨多个商家，钱由平台代收，再按周期结算给商家。核心问题有三个：订单怎么拆、钱怎么分、退款怎么退。

## 决策一：主单 + 子单

一次结算生成 **1 个主单 + N 个商家子单**（按 `merchant_id` 分组）。

| 层 | 谁看 | 管什么 |
|---|---|---|
| `orders` 主单 | 顾客 | 金额汇总、支付、售后入口、整单状态 |
| `merchant_orders` 子单 | 商家 | 发货、退款、结算 |
| `order_items` 行 | 双方 | 商品快照，挂在子单下 |

不采用「一个订单多个商家」的单表方案，原因：发货与退款天然按商家独立，单表会让状态字段变成多值含义，查询与并发都难写。

## 决策二：主单状态由子单聚合

主单只保留支付与聚合语义的状态：`待付款 → 已付款 → 部分发货 → 已发货 → 已完成`，以及 `已取消`、`已退款`。

聚合规则（每次子单变更后重算）：

| 子单情况 | 主单状态 |
|---|---|
| 全部待发货 | 已付款 |
| 部分发货、部分待发货 | 部分发货 |
| 全部发货、未全部完成 | 已发货 |
| 全部完成 | 已完成 |
| 全部退款完成 | 已退款 |

聚合在事务内直接计算写回，不用事件异步——量级小，一致性优先。

## 决策三：平台代收 + 按子单结算

- 顾客支付一次，钱进平台账户（模拟环境只记账）
- 佣金按商家费率 `merchants.commission_rate`（基点），默认 500 = 5%
- 结算口径：**子单已完成 + 已过售后保护期**才可结算，避免「结算后又被退款」
- 结算单按商家 + 周期生成，一条 `settlements` + 多条 `settlement_items`
- 首版不做到账、提现、发票，只出结算单（可导出）

## 决策四：退款按子单

- 顾客对某个子单申请整单退款，金额 = 该子单实付
- **商家审核**（谁卖谁负责），平台客服可介入强制退款
- 退款成功后主单重新聚合；子单转「已退款」，对应库存回补规则沿用 ADR-0004

## 决策五：优惠券只做平台券

首版不做商家券，避免「优惠由谁出资、怎么分摊」的复杂账。平台券折扣按子单商品金额比例分摊，商家结算按分摊后的实收金额计算。

## 后果

- 购物车必须按商家分组展示；结算页要显示「共 N 个包裹，来自 M 个商家」
- 订单详情页是「主单 + 子单折叠」结构，顾客能分别看每个包裹的状态
- 商家后台与平台后台是两套菜单、两套权限，共用同一套用户体系
- 结算需要定时任务与对账 SQL（`Σ settlement_items = Σ 已完成子单实付 - 佣金`）

## 何时重审

引入商家券、平台补贴、部分退款、跨境税费时，结算模型需要重做。
