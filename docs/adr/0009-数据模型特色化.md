# ADR-0009 商品属性扩展：多维标签、档案、定制项、礼物（原：手作市集数据模型）

## 修订（2026-10-28）

初版把数据模型的出发点写成"手作市集"，容易被理解成垂直小众站。修正：KDShop 是**多品类商城**，8 个通用类目 + 手作家居/文具/礼物三个特色专区。下列结构不专属于手作：

- 多维标签：任何类目都能挂工艺/材质/场景，用于运营与筛选
- 商品档案（限量、孤品、故事、瑕疵披露）：定制/限量类商品使用，普通商品留空
- 定制项：可用于刻字、尺寸、颜色等任何需要下单时确定的选项
- 礼物字段：全站可用

- 状态：已接受
- 日期：2026-10-28

## 背景

现有 26 张表是标准通用商城结构：一棵类目树、商品挂 SKU、订单拆子单。这套模型放进任何电商项目都成立，因此也看不出这是个什么平台。

通用商城的商品表答不了几个问题：这件东西是谁做的、用什么做的、做了多久、有没有瑕疵、能不能改。这些属性同样适用于数码定制、服饰定制等类目。ADR-0008 定了"定制交易 + 售后闭环"的定位，但数据层如果没有对应结构，功能就会悬空。

## 决策

### 1. 分类从一棵树变成"树 + 三维标签"

- `categories` 保留，只承担**品类**（家居 / 文具 / 礼物）
- 新增 `tags`：维度 `CRAFT`（陶艺、金工、木作、织造、纸艺）、`MATERIAL`（粗陶、黄铜、胡桃木、亚麻、羊毛）、`OCCASION`（送恋人、乔迁、生日、自用）
- `product_tags` 多对多，一个商品可同时是"陶艺 / 粗陶 / 乔迁"

不采用"多维都做成树"：三维交叉用树表达会出现大量空节点，且筛选要多次联表。

### 2. 作品档案

| 字段 | 用途 |
|---|---|
| `edition_size` / `edition_no` | 限量 12 件里的第 3 件 |
| `is_unique` | 孤品，卖完不再有 |
| `story` | 创作故事，详情页"关于这件作品" |
| `flaw_note` + `requires_flaw_ack` | 手工痕迹说明；下单前必须勾选确认 |

"瑕疵披露需确认"是本模型最不像通用商城的一处：手作不可能完美，买家必须知情，这不是免责声明而是交易前置条件。

### 3. 定制项用"定义 + 快照"两张表

- `product_options`：选项定义（刻字 / 尺寸 / 颜色），类型 `TEXT` 或 `ENUM`，可加价
- `order_item_options`：下单时的值与加价快照

不采用"把定制内容写进订单备注"：备注无法参与金额计算，也无法在售后与质检里按选项追溯。

### 4. 礼物场景

`orders` 增加 `is_gift`、`gift_message`（≤100 字）、`gift_wrap`。下单页可勾选，发货邮件与包裹单带上。

### 5. 品类定为 家居 / 文具 / 礼物

用户拍板。种子数据里原有的"食品饮料 / 数码配件"等类目在 ISSUE-08 一并替换，避免模型与演示内容两张皮。

## 表变化

| 迁移 | 内容 |
|---|---|
| V3 | `products` 增加销售模式/工期/定金比例；`orders` 增加订单类型/定金/尾款/承诺发货时间/赔付；`payments` 增加 `purpose`；新增 `after_sales`、`after_sales_logs`、`penalties` |
| V4 | `products` 增加作品档案字段；`orders` 增加礼物字段；新增 `tags`、`product_tags`、`product_options`、`order_item_options` |

两版均为增量变更（只加列、加表），不改已有数据；已在空库上按 V1→V4 顺序验证，33 张表全部建成。

## 查询与索引

- 标签筛选：`product_tags(tag_id, product_id)` 反查，再与商品表按主键关联
- 多维组合（工艺 + 场景）：先按标签取交集，再分页，避免多次回表
- 商品详情：一次查 `product_tags` + `product_options`，前端一次渲染
- 100 SKU 量级下不需要额外倒排索引

## 被否的方案

| 方案 | 否决原因 |
|---|---|
| 全部维度做成类目树 | 交叉维度会爆炸，筛选逻辑复杂 |
| 标签用 JSON 存在 `products.tags_json` | 无法建索引，筛选要靠全表扫描 |
| 定制内容放订单备注 | 不参与金额、不可追溯 |
| 作品档案放 `description` 富文本 | 无法筛选（比如"只看孤品"）、无法驱动前端组件 |

## 后果

- 商品域从"一条记录"变成"记录 + 标签 + 选项 + 档案"，写入路径变长，需在 Service 层保证一致性
- 前端商品卡片、详情页、筛选器都要按新结构重做（ISSUE-08 范围扩大）
- 种子数据需要重写：类目、标签、带档案的定制商品

## 何时重审

若商品量超过 1 万、标签筛选成为瓶颈，再考虑把标签检索外置（ES 或 Redis 倒排）。
