# 权限矩阵（G0）

权限分两层：**功能权限**（能不能调这个接口）与**数据范围**（能看到谁的数据）。两层都满足才放行。

## 角色

`GUEST` 游客（未登录）、`CUSTOMER` 顾客、`SUPPORT` 客服、`OPERATOR` 运营、`ADMIN` 管理员。

## 数据范围

| 资源 | 顾客 | 客服 / 运营 | 管理员 |
|---|---|---|---|
| 订单 | 仅 `user_id = 当前用户` | 全量 | 全量 |
| 地址 | 仅本人 | 仅订单快照中可见 | 仅订单快照中可见 |
| 评价 | 自己的可改删 | 全量只读 | 全量 |
| 顾客资料 | 仅本人 | 脱敏（手机号中间四位掩码） | 全量 |
| 审计日志 | 无 | 无 | 全量 |

## 实现约定

- 接口级：`@PreAuthorize("hasRole('OPERATOR')")`；方法名与权限码一一对应
- 数据级：Service 层统一校验 `currentUser.id == resource.ownerId`，越权返回 403 而不是 404（除非需要隐藏资源存在性）
- 前端：菜单按角色渲染，但**不作为安全边界**——所有校验在服务端重做
- 会话：Spring Session + Redis，角色变更下一次请求即生效（不做 token 内嵌角色）

## 验收线

1. 顾客 A 请求顾客 B 的订单详情 → 403
2. 客服访问 `/api/admin/products` 的写接口 → 403（只读接口 200）
3. 普通顾客直接访问 `/admin` 前端路由 → 跳登录页；即使绕过前端，接口仍 403
4. 管理员修改某用户角色后，该用户下一个请求即按新角色鉴权
